# RanobeDays — Конституция разработки

Этот документ обязателен для всех следующих сессий и изменений в проекте.

## 1) Архитектура и компоненты

1. Любой UI писать **компонентами** с фокусом на переиспользование.
2. Не дублировать разметку/логику: выносить повторяющиеся паттерны в `ui`-компоненты и composables.
3. Новые фичи собирать через композицию маленьких компонентов, а не через монолитные файлы.
4. Компоненты должны иметь понятный API: `props`, `emits`, состояния без скрытой магии.
5. По умолчанию все компоненты проектируются **адаптивными** (mobile-first).

## 2) Качество и тестирование

1. Любой значимый функционал покрывать тестами.
2. Минимум:
   - unit-тесты для бизнес-логики и composables;
   - component-тесты для ключевых UI-сценариев;
   - smoke/e2e для критических пользовательских потоков.
3. Любой баг фиксить вместе с тестом, который предотвращает регрессию.
4. PR/изменение считается завершённым только когда тесты зелёные.

## 3) Код-стандарты и best practices

1. Следовать принципам: SOLID, KISS, DRY, YAGNI.
2. Имена сущностей должны быть однозначными и предметными.
3. Не использовать `any`/небезопасные обходы типизации без веской причины и комментария.
4. Ошибки не глушить: показывать/логировать явно, не делать «тихие» фейлы.
5. Рефакторинг делать безопасно и небольшими шагами.
6. Любые временные решения помечать как временные и фиксировать задачу на замену.

## 4) Конфигурация и секреты (.env)

1. Все важные/изменяемые параметры хранить в переменных окружения.
2. Секреты (ключи, токены, пароли, DSN) **никогда** не коммитить в репозиторий.
3. Держать `.env.example` с обязательными ключами и безопасными примерами.
4. Разделять конфиг и код (подход 12-factor).
5. Проверять наличие обязательных env-переменных при старте приложения.

## 5) Безопасность

1. Следовать OWASP Top 10 как базовому стандарту.
2. Валидировать и санитизировать входные данные на границах системы.
3. Не раскрывать внутренние ошибки/стектрейсы пользователю.
4. Минимизировать права доступа (principle of least privilege).
5. Использовать безопасные заголовки, безопасное хранение токенов и защиту от XSS/CSRF по контексту.

## 6) DX, CI/CD и окружения

1. Dev/stage/prod держать максимально похожими (dev/prod parity).
2. Линт, тесты, сборка — обязательные шаги перед мерджем.
3. В CI должны выполняться минимум: проверка форматирования/линта, тесты, сборка.
4. Изменения зависимостей — осознанно, с фиксацией версии и проверкой совместимости.

## 7) UX и продуктовые требования

1. UI должен быть консистентным: единые состояния hover/focus/active/loading/empty/error.
2. Любой интерактивный элемент должен иметь корректные состояния доступности.
3. Критичные сценарии (логин, чтение, поиск, закладки) должны быть удобны и на мобильных, и на десктопе.
4. Тексты интерфейса должны быть понятными и лаконичными.

## 8) Документация изменений

1. При добавлении новой фичи обновлять релевантную документацию.
2. Если введён новый env-параметр — обязательно обновлять `.env.example` и инструкцию запуска.
3. Если меняется архитектурное решение — кратко фиксировать причину в проектной документации.

## 9) Чеклист перед завершением задачи

1. Компоненты переиспользуемы и адаптивны.
2. Тесты добавлены/обновлены и проходят.
3. Секреты не попали в код, конфиг вынесен в `.env`.
4. Нет дублирования и «магических» констант.
5. Сборка и базовые сценарии работают.

---

**Правило по умолчанию:** если есть сомнение между «быстрее» и «качественнее», выбираем решение, которое снижает технический долг и риск регрессий.
